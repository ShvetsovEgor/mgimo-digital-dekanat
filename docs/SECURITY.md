# SECURITY — вход, хранение данных, защита (простым языком и технически)

## Простыми словами

1. **Вход.** Мы придумали каждый студент получает свой логин и пароль. Пароль мы не храним — храним только
   его «отпечаток» (хеш), по которому невозможно восстановить сам пароль. После входа браузер получает
   служебную cookie, которая действует, пока не выйдешь. Cookie не читается из JavaScript — её не украсть XSS-скриптом.
2. **Свои данные.** Каждый запрос к серверу начинается со служебной cookie, сервер сам узнаёт, кто ты
   (студент X или сотрудник деканата), а не по ссылке. Поэтому нельзя подставить чужой номер в адресе —
   сервер откажет: номер заявки или профиля проверяется на принадлежность именно тебе.
3. **Документы.** PDF-справку может скачать только её владелец. У документа есть QR-код, по которому любой
   (например, работодатель) может проверить подлинность на сайте — но статус проверки не раскрывает персональные данные.
4. **Секреты.** Пароли, ключ подписи и настройки хранятся в переменных окружения на сервере, не в коде
   и не в браузере. В репозиторий они не попадают.
5. **Данные вымышлены.** Все ФИО, адреса и номера зачёток придуманы. Прототип не связан с системами вуза.

## Технически

### Аутентификация
- Пароли: `bcryptjs`, cost 11 (регулярно пересчитывается до `BCRYPT_ROUNDS` при входе).
- Политика пароля: ≥ 8 символов, не равен логину (сервер + клиент).
- Сессионные токены: 32 случайных байта (`crypto.randomBytes`), храним **SHA-256** хеш токена в БД;
  в cookie — `httpOnly`, `secure` (в проде), `sameSite: 'lax'`, `path: '/'`; в проде имя cookie — `__Host-dl_session`
  (защищает от подделки с поддомена).
- Срок жизни 30 дней, «скользящее» продление при активности, отзыв всех сессий по кнопке.
- Brute force: 10 неудач на (IP-хеш + логин) за 15 мин → HTTP 429.
  Одинаковый ответ на неверный логин и неверный пароль.
- Смена пароля требует текущего пароля, после смены отзываются все остальные сессии.

### Авторизация (RBAC + ownership)
- `requireAuth` и `requireRole('staff')` middleware.
- Любое обращение к ресурсу пользователя: `WHERE id = ? AND user_id = ?`. При несовпадении — **404** (не раскрываем существование).
- Сотрудник видит только заявки своего деканата (`department_id`).
- `GET /api/requests/:id/document` дополнительно проверяет `status = 'ready'`.

### Заголовки и CSRF
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy`, `Content-Security-Policy` (без `unsafe-eval`; стили Tailwind + инлайн-стили прогресса —
  `style-src 'self' 'unsafe-inline'`; шрифты Google — `font-src`).
- Все не-GET API-запросы принимаются только с `Content-Type: application/json` + проверка `Origin`/`Sec-Fetch-Site`.
- `express.json({limit:'64kb'})`, входные данные валидируются zod, строки экранируются React'ом.

### Подпись документов
- QR содержит `https://host/verify/<payload>.<mac>`, где `payload = base64url({n: номер, t: unix-время})`,
  `mac = HMAC-SHA256(payload, DOC_VERIFY_SECRET)`.
- `/api/verify/:token` проверяет HMAC за постоянное время (`crypto.timingSafeEqual`) и возвращает только
  «подлинный/не подлинный», номер и дату.
- Ключ `DOC_VERIFY_SECRET` — только в env.

### Хранение
- SQLite (better-sqlite3), WAL, БД в `./data`, не в репозитории. Для масштабирования — PostgreSQL: доступ только через
  слой `db.ts`/`repo.ts`, SQL простой.
- Логи без PII: логируется метод, путь, статус, время; тело и пароли — никогда.

### Проверка
- `server/tests/security.test.ts` — автоматические тесты: IDOR по заявкам, чужим профилям, документам;
  отсутствие сессии; роль сотрудника; rate-limit; изменение чужого статуса.
